# Uranus 插件市场

这里是 [Uranus](https://github.com/nikonotnicotine/Uranus_Imessage) 社区插件的**链接目录**。

**这个仓库里一行插件代码都没有。** 只有一份 [`plugins.json`](plugins.json) —— 每条记着插件的名字、说明、作者和仓库地址。你在 Uranus 控制台的「插件市场」里看到的列表就是它。点一个插件，跳到作者自己的 GitHub 仓库，下载 zip，回控制台装上。

---

## ⚠️ 装插件之前请读这段

**收录不代表安全。** 这份目录由一个人在业余时间维护。我们会在收录前看一遍代码，但：

- 我们**不是**专业的安全审计，看漏东西是常态而不是意外；
- 我们看的是**提交那一刻**的代码。插件由作者自己维护，收录之后作者随时可以改，那些改动不在我们的审查范围内；
- 我们**不托管、不分发、不修改**任何插件代码 —— 你下载到的文件来自作者的仓库，中间没有经过我们。

**插件在你的 Uranus 里拥有和主程序相同的权限。** 它能读写你的聊天记录、角色设定、记忆库，能看到你配置的 API 密钥，能替你调用任何接口。装一个插件 ≈ 让一个陌生人在你的服务器上跑代码。

**我们不保证任何插件没有 bug、不丢数据、不出安全问题。** 因安装或使用插件造成的数据丢失、凭据泄露、费用产生或任何其它损失，由使用者自行承担。

能帮上忙的几件事：

- 装之前花两分钟翻一眼源码，尤其是有没有往陌生地址发请求；
- 优先装标了「已锁定版本」的插件 —— 那些指向一个固定的 release，和我们审过的是同一份；
- 看一眼卡片上的「审核于 ⋯⋯，之后作者有 N 次提交」。数字很大就自己留个心；
- 装之前把 `data/` 备份一下。

发现问题请[举报](https://github.com/nikonotnicotine/uranus-plugins/issues/new?template=report-plugin.yml)。**安全问题别公开提 issue**，走 [SECURITY.md](SECURITY.md) 里的私下渠道。

## 上架规则

### 必须开源

插件必须采用一个 [OSI 认证](https://opensource.org/licenses)的开源协议，并且仓库根目录要有对应的 `LICENSE` 文件。允许的协议见 [schema](schema/plugins.schema.json) 里的清单，常见的 MIT、Apache-2.0、GPL-3.0 都在。

CC-BY-NC 这类「禁止商用」的授权**不是**开源协议，不收。

### 不收含付费内容的插件

插件不得包含任何形式的付费内容：收费功能、订阅、付费解锁、内购，或者引流到付费群 / 付费服务 / 付费教程。违反的会被移到 [`delisted.json`](delisted.json)，并且所有装过它的用户都会在控制台里看到警告。

**这是本目录的准入规则，不是对你协议的限制。** 开源协议（MIT、Apache-2.0 这些）本身都允许商业使用，我们也不干涉你拿自己的代码去做什么 —— 只是含付费内容的插件不收进这份目录。这两件事别混在一起：代码的自由归协议管，收不收录归目录管。

### 代码要能读

混淆过、压缩成一坨、或者只有构建产物没有源码的插件一律退回。**看不懂的代码等于审不了**，这不是态度问题。

### 其它

- 仓库必须公开，不需要登录就能访问；
- `author` 填的 GitHub 账号必须和仓库 owner 是同一个 —— 不收代投，你得用自己的账号来;
- 一个仓库只能上架一条；
- 描述要和插件实际做的事对得上。

## 怎么上架

**上架走 Pull Request，不走 issue。** 还没写插件的话先看[怎么写一个插件](WRITING-PLUGINS.md)。

1. 把插件代码推到你自己的 GitHub 仓库（公开），根目录放好 `LICENSE`。

2. **建议**给它打个 tag 发一个 release。这样目录可以指向一个固定版本，用户下载到的永远是我们审过的那一份，你之后改主分支也不会影响已上架的版本 —— 市场卡片上会标「已锁定版本」，用户更愿意装。想更新就提 PR 改 `lockedVersion`，走一次复审。

3. Fork 这个仓库，往 [`plugins.json`](plugins.json) 的 `plugins` 数组里加一条：

   ```json
   {
     "id": "uranus-plugin-weather-card",
     "title": "天气卡片",
     "desc": "在聊天里插入一张实时天气卡片，支持多城市切换和农历显示。",
     "author": "https://github.com/someone",
     "repo": "https://github.com/someone/uranus-plugin-weather-card",
     "license": "MIT",
     "tags": ["界面", "工具"],
     "lockedVersion": "v1.0.0",
     "reviewedAt": "2026-11-24",
     "reviewedCommit": "0000000000000000000000000000000000000000"
   }
   ```

   - `id` 要和插件 `manifest.json` 里的 `id` 一致 —— 控制台靠它判断「这个你已经装了」；
   - `reviewedCommit` 填你本次提交对应的**完整 40 位** commit SHA（`git rev-parse HEAD`）；
   - `reviewedAt` 先填今天，审核时我们会改成实际过审的日期；
   - `addedAt` 不用填，合并时自动补。

4. 本地跑一下，省得来回推：

   ```powershell
   node scripts/sort.mjs
   node scripts/validate.mjs
   ```

   没联网或者被 GitHub 限流就加 `--offline`，只跑格式检查。

5. 提 PR，把模板里每一栏都填掉。**空着的栏会被直接退回** —— 不是因为态度，是因为没法审。

### 之后会发生什么

CI 先跑一遍机器能查的（格式、链接通不通、`LICENSE` 在不在、commit 和 tag 是不是真的）。红了你自己看报错改，这一步不用等人。

绿了之后等人工审核。**CI 全绿不等于会合并** —— 代码有没有在偷数据、权限声明和实际行为对不对得上、有没有付费内容，这些只有人能看。

维护者一个人,业余时间看，**可能要等几天**。催更不会变快，但如果超过两周没动静，在 PR 里 at 一下是完全可以的 —— 多半是漏看了。

同一个账号第二次提 PR 会快很多。

## 审核看什么

写在这里是为了让作者知道自己会被看什么，也让维护者有个一致的标准。

机器查（CI，红了就退，不用人看）：

- `plugins.json` / `delisted.json` 的格式，字段齐不齐、合不合规；
- `id` 和 `repo` 有没有和已有条目撞；
- `author` 和 `repo` 的 owner 是不是同一个账号；
- 仓库是不是公开、是不是已归档、有没有改名;
- 根目录有没有 `LICENSE`，GitHub 识别出来的协议和声明的是不是一个;
- `reviewedCommit` 这个 commit、`lockedVersion` 这个 tag 是不是真的存在;
- 条目有没有按 id 排序（减少 PR 冲突用）。

人工看（必过，没法省）：

- 仓库里确实有插件，不是空仓库占位；
- 标题和描述跟仓库实际做的事对得上，没有夸大、没有骗量；
- `manifest.json` 声明的权限和代码实际在干的事一致 —— 声称只改界面却在调 `/api/config` 这种直接退；
- 读 `data.config.json`、读 `auth.json`、往外发网络请求的地方，**必须看明白它为什么要这么做**；
- 代码没有被混淆或压缩；
- 没有付费内容。

审核者合并前要把 `reviewedAt` 和 `reviewedCommit` 改成**实际过审**的日期和 SHA，不能直接用作者填的。

### 我们审不到的

**收录后作者改代码，我们不知道。** 目录指向的是仓库主页（没填 `lockedVersion` 的话），用户点进去下载的永远是最新代码。所以一个作者完全可以提一个干净的插件过审，一周后往里塞东西 —— 对此我们的审核无效。

能缓解的两件事，但都不能根治：

- 索引里记着过审时的 commit SHA，控制台会显示「审核于 ⋯⋯，之后作者有 N 次提交」，让用户自己判断;
- 填了 `lockedVersion` 的插件指向一个固定的 release，这个是真能堵住的 —— 所以我们强烈建议作者走 release，也建议用户优先装标了「已锁定版本」的。

这是链接目录模式的固有缺口。要彻底堵上就得托管代码、锚定内容哈希、自建 CDN，那是另一个量级的工程，现阶段不做。**所以请回去再读一遍最上面那段免责声明。**

## 下架

出问题的插件从 [`plugins.json`](plugins.json) 删掉，**同时**在 [`delisted.json`](delisted.json) 里加一条。两边必须同步 —— 同一个 id 同时出现在两份文件里，用户会看见「可以装」和「有安全问题」同时弹出来，CI 会拦这种情况。

控制台每次拉目录都会对照这份名单：本地装了已下架的插件就亮红色警告，`reason` 是 `security` 的会弹得更重。

**审核总会漏，召回不能漏。** 这份名单比审核本身更重要。

作者想主动下架随时提 PR，`reason` 填 `author-request`，不用给理由。

## 给集成方

两份 JSON 直接读 raw 就行，不需要鉴权：

```
https://raw.githubusercontent.com/nikonotnicotine/uranus-plugins/main/plugins.json
https://raw.githubusercontent.com/nikonotnicotine/uranus-plugins/main/delisted.json
```

格式见 [`schema/`](schema/)。`version` 字段只在字段含义变了的时候才加，加条目不算 —— 照着它判断兼容性。
